# Publishing envseal

Nine packages ship to npm as one lockstep release:

| Package | bin |
| --- | --- |
| `@envseal/protocol` | — |
| `@envseal/registry` | — |
| `@envseal/detector` | — |
| `@envseal/prompters` | — |
| `@envseal/core` | — |
| `@envseal/sdk` | — |
| `@envseal/http-server` | — |
| `@envseal/mcp-server` | `envseal-mcp` |
| `@envseal/cli` | `envseal` |

`plugins/claude-code` and `extensions/vscode` are `private: true` and are never published;
they ship through the Claude Code plugin marketplace and the VS Code marketplace instead.

## The one rule: never `npm publish`

Seven of the nine packages depend on their siblings through pnpm's `workspace:*` protocol.
`npm publish` and `npm pack` **do not rewrite it** — they copy the manifest verbatim, so the
tarball goes out carrying:

```json
"dependencies": { "@envseal/core": "workspace:*" }
```

and every install of that tarball dies:

```
npm error code EUNSUPPORTEDPROTOCOL
npm error Unsupported URL Type "workspace:": workspace:*
```

npm has no way to resolve `workspace:` outside a workspace, so this is not a warning the user
can work around. The only remedy after the fact is unpublishing (24-hour window) or burning a
version number. `pnpm publish` rewrites `workspace:*` to the concrete version (`"0.1.0"`)
before uploading.

Three things enforce this so it cannot happen by accident:

1. **`prepublishOnly` on all nine packages** runs `scripts/release-guard.mjs`, which aborts
   unless `npm_config_user_agent` says pnpm. `npm publish` in any package directory fails
   before it uploads anything. (pnpm strips publish lifecycle scripts from the published
   manifest, so this hook does not reach consumers.)
2. **`scripts/release.mjs`** (`pnpm release`) is the release path. It does not trust the
   manifests: it packs all nine packages and greps the *packed* `package.json` inside each
   tarball for a surviving `workspace:` specifier, and refuses to publish if it finds one.
3. **`.github/workflows/release.yml`** is where a real release runs.

The guard has an escape hatch, `ENVSEAL_ALLOW_NPM_PUBLISH=1`. Do not use it. It exists so the
failure mode is a deliberate override rather than someone deleting the guard under time
pressure.

## Releasing

Local preflight — packs everything, checks the tarballs, uploads nothing:

```
pnpm release:dry
```

Real release: push a `v*` tag (or run the Release workflow with **dry-run** unchecked).
The workflow runs build, typecheck, test and lint, then the preflight, then `pnpm -r publish`.

Publishing from a laptop is not supported. It has no OIDC token, so `publishConfig.provenance`
makes npm reject it (see below).

## Access

Every package sets:

```json
"publishConfig": { "access": "public", "provenance": true }
```

All nine names are scoped (`@envseal/*`), and npm defaults scoped packages to **restricted**.
Without `access: "public"` the very first publish of the `@envseal` scope fails — and on a free
npm account, restricted packages are not permitted at all. `npm publish --dry-run` reports the
resolved value; it must say `public access`, not `default access`.

## Provenance

npm's provenance attestation is a signed, publicly verifiable statement binding the tarball to
the commit and workflow that built it. For a tool whose whole pitch is "your agent never sees
the secret", supply-chain attestation is worth keeping, so it is **not** dropped in the move
away from `npm publish --provenance`.

It survives the move because provenance is generated by npm, not by the `--provenance` flag
specifically, and there are three ways to ask for it. This repo uses two of them together:

- `publishConfig.provenance: true` in each manifest. pnpm writes the rewritten manifest into
  its staging directory and invokes npm there, so npm reads the field exactly as it would for a
  direct `npm publish`. This is the declarative belt: it applies no matter how the publish is
  invoked.
- `NPM_CONFIG_PROVENANCE: 'true'` in the workflow environment. npm reads its whole config from
  `NPM_CONFIG_*`, independent of argv, so this survives any wrapper.

(`pnpm publish --provenance` is also accepted — pnpm rejects unknown flags and accepts this one
— but a flag is easy to drop from a command line, so it is not what the release relies on.)

The attestation needs a GitHub OIDC token, which is why the release job declares:

```yaml
permissions:
  contents: read
  id-token: write
```

Without that token npm refuses to publish rather than silently shipping an unattested tarball.
That is the intended behaviour: a publish from a developer machine should fail.

**Unverified:** provenance generation has not been exercised end to end — that requires a real
registry and a real Actions run. What has been checked locally is that pnpm accepts
`--provenance`, and that `publishConfig.provenance: true` does not disturb `npm publish
--dry-run` or `pnpm publish --dry-run`.

## Source maps are not published

`tsconfig.base.json` sets `sourceMap` and `declarationMap`, so `dist/` contains `*.js.map` and
`*.d.ts.map`. Their `sources` point at `../src/*.ts` and there is no `sourcesContent`, and
`src/` is deliberately not in the tarball — so every published map resolved to nothing. A
dangling map is worse than no map: it makes debuggers and stack-trace tooling silently show the
wrong thing.

The fix is one line per package:

```json
"files": ["dist", "!dist/**/*.map"]
```

Maps are still emitted into `dist/` and still work for anyone building from source; they just
do not ship. The release preflight fails if a `.map` ever reappears in a tarball.

The alternative — `"inlineSources": true` in `tsconfig.base.json` — would embed the TypeScript
source into the `.js.map`, but it does nothing for `.d.ts.map`, whose entire purpose is to jump
into a `src/` tree that is not shipped. It would also publish the full source inside every
tarball as a side effect. If shipping source is ever wanted, do it deliberately by adding
`src` to `files`, not as a by-product of a compiler flag.

## The workspace does not include the example

`pnpm-workspace.yaml` used to list `examples/*`, which matched nothing — there is no top-level
`examples/` directory. The sample agent lives at `packages/examples/custom-agent`, and
`packages/*` does not reach it either, so it has never been installed, typechecked or built.

The dead glob is removed rather than repointed, because `packages/examples/*` does not compile
today:

```
src/agent.ts(25,5): error TS2322: Type 'StubPrompter' is not assignable to type 'Prompter'.
    Type '"stub"' is not assignable to type 'PrompterId'.
src/stub-prompter.ts(16,7): error TS2353: Object literal may only specify known properties,
    and 'keys' does not exist in type 'PromptResponse'.
error TS5083: Cannot read file '.../packages/tsconfig.base.json'.
```

The example is written against an older SDK surface, and its `tsconfig.json` extends
`../../tsconfig.base.json` from a directory that is three levels deep. Adding it to the
workspace as-is turns `pnpm -r build` and CI red. Fix those three things, then add
`packages/examples/*` to the workspace — an example that compiles against the published surface
is the cheapest proof that the public API is usable from outside.

## Verifying a tarball by hand

The check that matters is not `npm pack --dry-run`; it is installing the artifact somewhere
that is not this repo:

```sh
pnpm -r build
mkdir /tmp/envseal-check && cd /tmp/envseal-check && npm init -y
for p in protocol registry detector prompters core sdk http-server mcp-server cli; do
  (cd /path/to/env/packages/$p && pnpm pack --pack-destination /tmp/envseal-check/tgz)
done
npm install ./tgz/*.tgz
node -e "import('@envseal/core').then(m => console.log(Object.keys(m).length))"
node node_modules/.bin/envseal --version
```

If `npm install` prints `EUNSUPPORTEDPROTOCOL`, something packed with npm instead of pnpm.

## Known cosmetic warning

A clean `pnpm install` in this repo logs:

```
Failed to create bin at .../node_modules/.bin/envseal.EXE. ENOENT: ... 'packages/cli/dist/bin.js'
```

pnpm links workspace bins at install time, before `pnpm build` has produced `dist/bin.js`. It
is not a packaging defect: for a published tarball npm links the bin from the tarball's own
`dist/`, which is already there. Running `pnpm install` again after a build clears it. Do not
"fix" it by committing `dist/` or by moving the bin out of `dist/`.
